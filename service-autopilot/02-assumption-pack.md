# Assumption Pack

| # | 가정 | 근거 | 틀릴 경우 영향 |
|---|---|---|---|
| A-01 | 운영 표준 태깅은 Haystack 우선으로 둔다. | 사용자가 Haystack으로 우선 구현 의사를 밝혔다. Haystack은 BMS/IoT 데이터 태깅 실무에 직접적이다. | Brick 중심으로 바꾸면 DB의 관계 모델, export 형식, 검증 로직이 달라진다. |
| A-02 | Brick은 초기 DB의 주 저장 모델이 아니라 호환 매핑 레이어로 둔다. | Brick은 관계 그래프 표현이 강하다. 초기에는 포인트리스트 정규화와 태깅 룰 생성이 더 급하다. | Brick 기반 분석/쿼리를 1차 목표로 하면 RDF/graph store 또는 graph export가 앞당겨진다. |
| A-03 | 표준 장비 템플릿과 현장 장비 인스턴스를 분리한다. | 같은 AHU/VAV/VFD라도 현장명, object id, 장비 모델, 포인트 노출 범위가 다르다. | 분리하지 않으면 한 현장의 naming noise가 전체 표준에 섞인다. |
| A-04 | 포인트리스트는 raw import 그대로 보존한다. | 인코딩, 오타, 중복, 벤더별 naming이 이후 검증 근거가 된다. | raw를 버리면 자동 태깅 오류를 추적하기 어렵다. |
| A-05 | 장비 spec은 포인트리스트가 아니라 제조사 문서/통신 맵/시퀀스 문서를 증거로 보강한다. | 포인트리스트에는 모델명, 제어 의도, enum/알람 코드, 쓰기 가능 여부가 부족하다. | spec을 포인트명에서만 추론하면 시뮬레이터와 자동제어 쪽에서 잘못된 모델이 생긴다. |

## 확정된 답변 반영

- 1차 범위: 장비/포인트 표준 대장 + Haystack 태깅 표준화
- 후속 범위: 현장 장비 자동 매핑 + 제어/AI 분석 기반
- 대상 장비: 모든 자동제어 장비
- 원천 데이터: 우선 BIOT 포인트리스트 제공 가능. 추가 원천은 조사/수집 필요.
- 배포/사용: NEUROS와 외부 BMS/자동제어 시뮬레이터에서 모두 사용
