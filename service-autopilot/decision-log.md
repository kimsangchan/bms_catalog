## D-009: 기준 DB 엔진과 배치

- 날짜: 2026-07-27
- 결정: **PostgreSQL 단일, 사내 중앙 1인스턴스.** 현장마다 설치하지 않는다.
- 근거: NEUROS의 MSSQL·PostgreSQL 양립 요구는 *현장 배포물*에 걸린 제약이고, 기준 DB는 현장 배포물이 아니다. 30여 테이블에 이중 DDL·`databaseIdProvider` 유지비를 지불할 대가가 없다.
- 버린 대안: MSSQL + PostgreSQL 이중 지원
- 상태: **가정 채택 (사용자 확인 권장 — A-06)**. 뒤집힐 경우 영향은 `06-architecture.md` "검토한 대안" 말미에 명시
- 재검토 트리거: "현장 로컬 기준 DB"가 요구될 때

## D-010: 적용 경로 — 시스템 중립 + 어댑터 확장

- 날짜: 2026-07-27 (초안) → **2026-07-27 사용자 답변으로 강화·확정**
- 사용자 답변 원문: *"이건 bms 시스템이든 neuros 든 모두 사용할 수 있는 확장성을 고려해야해"*
- 결정: 코어는 **시스템 중립 표준 페이로드**(FR-070)만 생산하고, 시스템별 번역·호출은 **어댑터 SPI**(FR-071)가 전담한다. NEUROS REST는 어댑터 한 종류일 뿐이다. 어댑터는 **지원 능력을 선언**하고 미지원 항목은 `unsupported`로 항목 단위 보고(FR-072). 시스템 코드는 **개방 레지스트리 테이블**(FR-073, CHECK 하드코딩 금지). 어댑터 형태는 REST·파일/번들·표 내보내기 최소 3종(FR-074). 대상 시스템 DB 직접 쓰기는 금지.
- 근거: BMS마다 오브젝트 개념·코드·지원 기능이 다르다. 한 시스템 용어로 코어를 만들면 두 번째 시스템에서 재작성이 된다. 실측이 이미 증거다 — 같은 `MSO`가 NEUROS `7` / BACnet `14` / Niagara `Multi State Output`으로 갈린다.
- 버린 대안: ⑴ 대상 BMS DB 직접 쓰기(BMS마다 DB 구조가 달라 확장 불가) ⑵ NEUROS 전용으로 만들고 나중에 일반화(용어가 스며들어 재작성이 됨) ⑶ NEUROS 공개 REST 경유 *한 가지만* 지원(초안 — 확장성 요구에 미달)
- 상태: **확정** (A-07)
- 검증: SC-013 코어 diff 0줄 · SC-014 미지원 항목 단위 보고 · SC-015 페이로드에 특정 BMS 용어 0건
